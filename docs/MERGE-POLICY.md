# 合并批次与决策

状态：现行流程。目标不是“合得快”，而是**每一批都能独立解释、独立验证、独立回退**。

参考的智能体架构：Reasonix（[`esengine/DeepSeek-Reasonix`](https://github.com/esengine/DeepSeek-Reasonix)，MIT，2026-11-12 归档）的工程契约，截止 2026-11-17 查阅的是其 [`docs/SPEC.md`](https://github.com/esengine/DeepSeek-Reasonix/blob/studio/docs/SPEC.md)。可借鉴的不是某个框架名，而是这些边界：

- 契约先行：先改 spec / 接口，再改实现。
- 注册表 + 两层扩展：内置能力与外部插件分离，核心不硬编码具体模型 / 工具。
- 缓存优先、追加式历史：少改已经稳定的前缀，压缩是少见的“缓存重置点”。
- 每次工具调用单独判定权限；deny 永远优先。
- 子任务完成声明由宿主按回执裁决，模型自述不算证据。
- 子 agent 上下文显式继承；写入路径声明在调度和执行两侧同时生效。
- 并行任务是小依赖图，不是无限 fan-out；依赖成环在启动前失败。
- MCP 只读不等于无状态；并发要尊重连接和会话边界。

本仓库的合并流程借用它的“规划 / 执行 / 验证分离”，但**不把合并权交给自动 agent**。自动 agent 可以拆批、跑检查、生成报告；人类所有者保留最终合并与许可变更决定权。

## 1. 一批是什么

一个批次 = 一个可命名能力，包含：

```text
1. 契约：新增 / 修改的公开 API、能力 id、schema、错误码
2. 实现：最小必要代码，不夹带无关重构
3. 测试：成功、失败、边界、回归；必要时差分测试
4. 文档：对应 docs 与 README 更新
5. 迁移：旧数据 / 旧前端 / 旧配置怎么办
6. 回退：revert 之外是否还需要锁能力 / 回滚数据
```

不满足以上六项，不算可合并批次。

规模建议：

- 一个批次只解决一个能力或一个明确缺陷。
- 纯逻辑改动控制在可一次读完的范围；超过约 600 行（不含测试 / 文档 / 生成代码）应拆分。
- 重构与行为变化分开；格式化与逻辑修改分开。
- 跨层改动必须拆成“下层先行 + 上层适配”两批，不能一个大 PR 同时改 L0/L1/L2/L3。

## 2. 批次顺序

```text
L0 语义 / 原生库
  -> L1 编排 / 裁决
    -> L2 宿主 / 执行 / 缓存 / 会话
      -> L3 前端 / 桌面 / 展示
```

规则：

- 下层没有稳定契约，上层不先合并 UI。
- 前端能力必须先在内核 `FeatureGate` 声明，再合并前端入口；反过来会导致“前端能点、内核不认识”。
- 数据格式 / 迁移先合，读取方后合；删除旧路径最后合。
- 安全修复可以跨层，但必须单独成批，不能藏在功能 PR 里。

## 3. 角色

| 角色 | 职责 | 不能做什么 |
| --- | --- | --- |
| Planner | 把需求拆成批次，写清依赖、验收、回退 | 不直接改代码；不替所有者做许可决定 |
| Executor | 实现一个批次，跑本地检查，填 PR 模板 | 不夹带未列出的改动；不自行放宽安全边界 |
| Verifier | CI、测试、差分、文档、能力门禁、性能基线 | 不用“看起来没问题”代替证据 |
| Arbiter | 所有者 / 指定维护者；处理冲突、API、许可、发布 | 不在没有验证的情况下强推 |

自动 agent 可以担任 Planner / Executor / Verifier 的一部分，但 Arbiter 必须是人类。自动生成“已审查”不能替代人类签核。

## 4. 合并决策矩阵

| 变更类型 | 最低验证 | 额外审批 |
| --- | --- | --- |
| 纯文档 / 注释 | 链接检查、拼写、事实核对 | 1 名维护者 |
| 测试 / 基准 | CI 全绿、无行为变化 | 1 名维护者 |
| 内部重构 | fmt / clippy / 全量测试、差分或基线 | 1 名维护者 |
| 公开 API / schema | 上述 + 兼容性测试 + 迁移说明 | 内核维护者 |
| 安全边界 / 沙箱 / 权限 | 上述 + 针对性攻击测试 + 威胁模型更新 | 所有者 + 安全负责人 |
| 许可 / 权益 / 品牌 | 法务 / 所有者签核 | 所有者 |
| 破坏性变更 | RFC / 迁移工具 / 弃用周期 | 所有者 |

“CI 绿”只是必要条件，不是充分条件。以下情况即使绿也不能合：

- 测试没有覆盖新分支，只覆盖了旧路径。
- 失败被 `#[ignore]`、重试、超时调大掩盖。
- 兼容性靠“用户会升级”假设，没有锁住旧前端。
- 迁移不可回退，或回退会丢用户数据。
- 性能改动没有基线，只有“感觉更快”。

## 5. 合并门禁

每个代码批次至少跑：

```text
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

按改动范围追加：

- **跨平台**：Ubuntu / Windows / macOS；ARM64 / LoongArch 至少 `cargo check`。
- **前端契约**：`FeatureGate` 单测 + 前端旧版本 / 缺 feature / 缺依赖 / 组 fail-closed。
- **缓存 / 上下文**：LRU / TTL / 压缩预算 / 迁移往返 / 低命中降级。
- **MCP / 并发**：并发资源读取、超时、取消、断线重连、背压。
- **安全**：symlink / 硬链接 / 路径穿越 / shell 写根 / 沙箱拒绝。
- **许可**：依赖许可证扫描、NOTICE、SPDX。

性能 / 成本相关改动（缓存、上下文、并发、模型调用）必须有前后对比数字；没有数字就当没做。

## 6. 停止条件

出现任一项，批次停在下游，不合并：

- 新增失败或 flaky 没有根因。
- 公开 API 变了但没有迁移说明。
- 新能力没有 `FeatureGate` 声明，前端已经先合。
- 依赖方向反转或成环。
- 许可 / 来源不明。
- 回退路径依赖未发布的工具。
- 跨平台编译失败被标记为“以后再修”。
- 文档与实现不一致，且没有明确哪一方是错的。

不允许用“先合了再修”绕过停止条件；紧急安全修复走单独热修流程，也要保留回退。

## 7. 回退

- 首选 `git revert` 新提交，不改写已推送历史。
- 数据 / 格式变更必须提供向前兼容读取或回滚脚本；不能只 revert 代码。
- 前端能力锁可以作为临时熔断：`FeatureGate` 默认关闭 / 锁住，不要求用户降级整个应用。
- 回退后补一条回归测试，防止同一问题再次进入。
- 不允许用 force-push 覆盖共享分支来“回退”；共享分支历史是审计证据。

## 8. 跨仓库合并

- 原生库（L0）先修 / 先发版，本仓再同步；不同时维护两套语义实现。
- Reasonix 这类上游移植按“能力”拆批，不按文件搬；每批写清来源、版本、MIT 声明。
- 每个移植批次附差分测试或行为对照，证明 Rust 实现与参考行为一致，或明确记录有意差异。
- 上游归档后，责任转移必须写进 [LIBRARY-STACK.md](LIBRARY-STACK.md)，不能默认“上游会修”。
- 跨仓 issue / PR 必须互相链接；合并说明写清依赖的版本 / commit。
