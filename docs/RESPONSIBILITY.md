# 责任、通知与升级

状态：现行流程。个人账号不写进本文，统一由各仓库 `.github/CODEOWNERS` 绑定角色；换人只改 CODEOWNERS，不改文档里的责任逻辑。

目标：任何问题都能回答四个问题——**哪一层坏了、谁先接手、修哪一层、通知谁**。避免“前端说内核没给、内核说前端没实现、最后没人修”。

## 1. 责任分层

| 层 | 范围 | 代码 / 仓库 | 首要责任角色 |
| --- | --- | --- | --- |
| L0 原生三进制 | `Ternary`、K3/Ł3/B3/Belnap、AST、位并行、指纹 | `bfxh/trit` 的原生库；本仓 `trit-core` 是抽取副本 | 原生库所有者 |
| L1 编排语义 | 调度、准入、义务 / 证据、预算、影子学习、Reasonix 裁决 | `trit-schedule`、`trit-orch`、`trit-reasonix` | 内核维护者 |
| L2 宿主 / 执行 | 模型 / 工具循环、MCP、工具边界、检查点、会话、缓存、上下文 | `trit-host` | 内核维护者 |
| L3 前端 / 桌面 | 界面、启动调度、游戏模式、扩展坞、通知展示 | 桌面 / Web 仓库 | 前端维护者 |
| L4 外部依赖 | 第三方 crate、模型 API、MCP server、Git / shell / OS | 上游 + 版本锁定 | 引入方（内核或前端） |

依赖方向只能从高编号指向低编号。L3 不能替 L0 做语义决定，L2 不能把前端 bug 推给模型。

## 2. 五类问题：谁负责、修哪里、通知谁

### 问题 1：三值语义 / 裁决错误

**症状**：`Unknown` 被当成假或真、Kleene 与 Ł3 混用、义务 / 证据结论不一致、Belnap 冲突处理错误。

- 首要责任：L0 原生库所有者；如果只在本仓抽取副本复现，由内核维护者先定位。
- 修复位置：L0 语义 / 测试；L1 若误用代数，修 L1 的调用。
- 通知：原生库仓库 issue，标签 `layer:L0`；跨仓同步到内核 issue。
- 证据：最小真值表 / 输入、期望值、实际值、受影响 crate 与提交。
- 升级：若影响完成裁决或安全，按 P0/P1 处理，两仓同时挂链接。

### 问题 2：执行 / 安全边界错误

**症状**：沙箱逃逸、symlink / 硬链接绕过、shell 写入越过工作区、MCP 工具越权、检查点无法回退。

- 首要责任：L2 内核维护者。
- 修复位置：工具边界、沙箱适配、检查点、MCP supervisor；第三方 MCP 的行为问题先加约束，再找上游。
- 通知：内核仓库安全渠道；可利用漏洞走私密安全公告，不在公开 issue 贴利用细节。
- 证据：平台、版本、复现命令、受影响路径、是否已有写入 / 数据损失。
- 升级：P0 立即走私密渠道；修复前默认关闭相关能力，不用“文档提醒”代替 fail-closed。

### 问题 3：上下文 / 缓存 / 会话错误

**症状**：压缩丢关键信息、缓存命中率异常、session 迁移丢失状态、checkpoint 恢复错位、token 预算计算错误。

- 首要责任：L2 内核维护者。
- 修复位置：`context_layers`、`context_tools`、`session*`、`checkpoint*`；涉及 L1 预算 / 证据时联动 L1。
- 通知：内核 issue，标签 `layer:L2`、`area:context` / `area:cache` / `area:session`。
- 证据：session JSONL（脱敏）、cache ledger、压缩前后 token、复现 turn、模型 / provider。
- 升级：数据丢失或不可恢复迁移按 P1；性能退化按 P2，但需附基线。

### 问题 4：前端 / 兼容 / 显示错误

**症状**：内核已更新但前端没入口、锁住的功能仍显示、扩展坞空壳打开、游戏模式没恢复、通知弹错人。

- 首要责任：L3 前端维护者；内核负责提供正确的 `GateReport` 和原因码。
- 修复位置：前端能力上报、可见性判断、组门禁、设置开关、恢复逻辑；内核契约错误才修内核。
- 通知：前端仓库 issue，标签 `layer:L3`、`compat:frontend`；内核 `notices` 的 owner 会自动指向这里。
- 证据：前端 `api_level` / features、内核版本、`GateReport`、截图或面板状态。
- 升级：整组扩展坞打不开按 P1；单个入口显示错误按 P2；文案问题按 P3。

### 问题 5：环境 / 配置 / 上游依赖

**症状**：没装 Git / bash、模型 API 变更、代理 / 证书、第三方 crate 版本冲突、用户配置写错、OS 权限不足。

- 首要责任：引入方（内核或前端）负责给出可诊断错误；环境本身由用户 / 运维处理。
- 修复位置：错误信息、预检、降级路径、版本锁定、上游 issue；不把环境问题包装成“内核 bug”。
- 通知：内核 issue 加 `area:environment`，或在对应上游仓库；需要用户操作时给明确步骤。
- 证据：`trit-host --version`、OS、依赖版本、错误日志、已尝试的配置。
- 升级：上游安全问题按上游流程；内核只做临时锁定 / 版本规避，并记录移除条件。

## 3. 五问分诊

收到问题先按顺序回答，答不出就停在“待补证据”，不要猜：

1. **哪一层？** L0 / L1 / L2 / L3 / L4；跨层就写主责层和联动层。
2. **哪个版本？** 内核版本、前端版本、`api_level`、模型 / provider、OS。
3. **是否越过边界？** 是否涉及写入、密钥、沙箱、用户数据、对外发送。
4. **有没有证据？** 回执、日志、session、cache ledger、最小复现；敏感内容脱敏。
5. **谁拥有契约？** 语义归 L0/L1，执行归 L2，显示 / 启动归 L3，第三方归 L4。

分诊结果必须落到一个 issue，带 `layer:*`、`owner:*`、`severity:*` 标签；不能只在聊天里解决。

## 4. 通知阶梯

| 级别 | 场景 | 通道 | 时限（最佳努力） |
| --- | --- | --- | --- |
| P0 | 安全漏洞、数据丢失、沙箱逃逸、供应链风险 | 私密安全公告 + 直接联系所有者；修复后再公开 | 立即 |
| P1 | 核心能力不可用、迁移失败、整组扩展坞打不开、完成裁决错误 | GitHub issue + 发布阻塞标记 + 直接通知主责 | 1 个工作日内分诊 |
| P2 | 单功能退化、缓存 / 性能异常、兼容性锁住 | GitHub issue + 对应标签 | 3 个工作日内分诊 |
| P3 | 文案、文档、易用性、非阻塞建议 | GitHub issue / discussion | 排期处理 |

通道说明：

- **GitHub issue**：默认入口；必须带分诊标签和证据。
- **安全公告**：P0 和可利用漏洞专用；不要在公开 issue 贴利用代码。
- **发布说明**：契约变化、能力锁、迁移步骤面向所有用户。
- **`GateReport.notices`**：运行时兼容缺口；按 owner 路由，进程内去重。
- **直接联系**：只用于 P0/P1；联系方式在团队内部配置，不写进公开仓库。
- **CI**：红线失败自动通知提交者；不把 CI 失败当“已经通知用户”。

## 5. 原始库与抽取副本的移交规则

这是最容易扯皮的地方，单独规定：

1. **问题在 `bfxh/trit` 原生库可复现**：归原生库所有者（你）。本仓只保留一个链接 issue，不重复修两套语义。
2. **问题只在本仓 `trit-core` 抽取副本复现**：归内核维护者；修完回填原生库测试，防止再次抽取时回归。
3. **两边都复现且根因相同**：上游先修，本仓同步抽取 / 升级；本仓可以临时加回归测试，但不长期保留分叉实现。
4. **不确定归属**：内核维护者先分诊，能复现就定位到层，再转交；不要同时 @ 两个人。
5. **上游已归档 / 不维护**：由本仓接管明确列出的 crate，并在 `LIBRARY-STACK.md` 更新责任角色；不能默认“上游会修”。

## 6. 证据与隐私

- 提交 issue 前删除 API key、token、Cookie、私密路径、完整会话内容。
- session JSONL、模型请求、工具输出都可能含敏感数据；只提供最小片段。
- 安全漏洞走私密公告；不要在公开 issue 里描述可直接利用的步骤。
- 责任方不能在未复现的情况下关闭 issue；至少说明缺哪个证据、下一步谁提供。

## 7. 责任变更

- 角色变更只改 CODEOWNERS 和发布说明，不改本文章节结构。
- 每季度检查一次：标签是否存在、CODEOWNERS 是否有效、P0 联系人是否可达。
- 没有 CODEOWNERS 的仓库视为“未接入责任机制”，发布前必须补齐。
