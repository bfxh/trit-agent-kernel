# 权益、许可与商业使用

状态：政策草案，不是法律意见。涉及具体商业条款、双许可、贡献者授权时，必须由所有者确认并在需要时咨询律师。

原则：**底层最宽，上层可以更严；但上层不能收回底层已经给出的权利。** 三进制原生库是地基，谁都可以在宽松许可下使用；官方桌面、云服务、商业插件可以有自己的更严格条款，但不能把 MIT / Apache 的代码重新闭源后再声称“原生库也归我独占”。

## 1. 分层权益

| 层 | 代码 | 许可 / 条款 | 商业使用 | 修改 / 分发 | 品牌 |
| --- | --- | --- | --- | --- | --- |
| L0 原生三进制 | `trit-core` | MIT OR Apache-2.0 | 允许 | 允许，保留版权 / 许可 / NOTICE；Apache 含专利授权 | 不自动获得项目商标 |
| L1 内核 | `trit-schedule` / `trit-orch` / `trit-reasonix` / `trit-host` | MIT OR Apache-2.0 + NOTICE | 允许 | 允许，保留声明；不得移除 NOTICE | 不自动获得“官方”标识 |
| L2 官方桌面 / 云 | 桌面、托管服务、企业版 | 单独商业条款 / EULA（如启用） | 按合同 | 按合同 | 可授权使用官方标识 |
| L3 插件 / 集成 | 第三方扩展、MCP server | 各自许可，必须声明 | 由作者决定 | 由作者决定 | 不得冒充官方 |
| 数据 | 用户会话、日志、模型输入输出 | 不随代码许可授予 | 用户保留权利 | 不适用 | 不适用 |

关键点：

- **L0 最宽**：允许嵌入、商用、修改、再分发；义务是保留版权与许可文本，Apache 路径保留 NOTICE 与专利条款。
- **L1 也是宽松许可**：可以在其之上做商业产品，但不能把 L1 说成比实际许可更严，也不能删除原作者署名。
- **L2 可以更严**：官方桌面 / 云服务可以是专有软件；它可以使用 L0/L1，但必须遵守 L0/L1 的许可，不能反过来限制别人使用 L0/L1。
- **“上层更严格”只作用于上层自己的原创代码**，不作用于下层已经授予用户的权利。

## 2. 允许与禁止

允许：

- 在商业产品中嵌入 L0 / L1，按其许可保留声明。
- 修改 L0 / L1 并分发，保留修改说明与许可。
- 提供基于 L1 的付费支持、托管、培训、集成服务。
- 为官方桌面 / 云服务采用单独商业条款。

禁止：

- 移除或替换 L0 / L1 的版权、许可、NOTICE 后声称是原创。
- 把 L0 / L1 的代码重新许可为更严格的专有条款，阻止他人行使原许可权利。
- 用项目名称、Logo、域名暗示“官方认证”，除非有单独品牌授权。
- 把用户数据、会话内容当作代码许可的一部分出售或再许可。
- 在未获得贡献者授权的情况下，把外部贡献单方面纳入闭源再许可。

## 3. 商业模型

建议的开放核心模型：

| 产品 | 内容 | 条款 |
| --- | --- | --- |
| 开源内核 | L0 / L1 / 无头 L2 | MIT OR Apache-2.0 |
| 官方桌面 | 更好的 UI、启动调度、游戏模式、自动更新 | 商业 EULA / 订阅 |
| 企业支持 | SLA、私有部署、审计、培训 | 商业合同 |
| 托管服务 | 云端会话、团队协作、计量 | 服务条款 + 隐私政策 |
| 商业插件 | 企业连接器、行业能力 | 单独许可 |

双许可（开源 + 商业）只有在贡献者授权清晰时才可行。当前若没有 CLA，不应假设可以把外部贡献直接用于闭源商业许可；需要所有者决定采用 DCO 还是 CLA，并在 `CONTRIBUTING.md` 写清。

## 4. 贡献者授权

当前建议：

- 使用 DCO（Developer Certificate of Origin）要求提交者声明有权提交。
- 入站 = 出站：贡献按本仓库许可提供，除非另有明确书面约定。
- 若未来要做双许可 / 闭源再许可，先补 CLA 或贡献者授权，再接受对应贡献；不能追溯假设。
- 提交者必须保证没有复制不允许的代码；移植 MIT 代码要保留声明。
- AI 生成代码同样要审查来源与许可，不能因为“是模型写的”就跳过。

## 5. 移植 Reasonix 的特别规则

Reasonix（[`esengine/DeepSeek-Reasonix`](https://github.com/esengine/DeepSeek-Reasonix)）是 MIT 许可，已于 2026-11-12 归档，最终版本 v2.61.0。可以研究其架构、移植能力，但：

- 直接复制代码：保留 MIT 版权与许可文本，标注修改。
- 只借鉴架构 / 文档：在 `MERGE-POLICY.md` 或提交说明中注明参考来源与版本。
- 不因为“上游归档”就删除署名；MIT 义务继续有效。
- 不把 Reasonix 的名称、Logo 用作本项目的官方标识。
- 移植后的 Rust 代码可以采用本仓库许可，但必须保留原 MIT 声明与 NOTICE（如适用）。

## 6. 所有 GitHub 仓库的落地清单

每个仓库发布前检查：

- [ ] `LICENSE`（或 `LICENSE-MIT` + `LICENSE-APACHE`）存在且 SPDX 正确。
- [ ] `NOTICE`（Apache 路径）与第三方许可证清单可生成。
- [ ] `RIGHTS.md` 说明本仓库层级、商业使用、品牌与数据边界。
- [ ] `CONTRIBUTING.md` 写清 DCO / CLA、入站许可、移植规则。
- [ ] `SECURITY.md` 写清私密报告渠道。
- [ ] `CODEOWNERS` 绑定责任角色，不写个人临时账号。
- [ ] 源文件 SPDX 头（至少新文件；存量逐步补）。
- [ ] 依赖许可证扫描进入 CI（允许清单 + 人工复核例外）。
- [ ] 商标 / 名称使用政策；官方与非官方标识区分。
- [ ] 发布说明包含许可或权益变化。

本仓库当前已有 MIT / Apache 双许可文件；`RIGHTS.md` 是政策入口。`NOTICE`、第三方许可证清单、CODEOWNERS、SPDX 头属于待补齐项，不能因为文档写了就当作已存在。

## 7. 冲突与变更

1. 许可变更必须由仓库所有者签核，并在发布说明中单独列出。
2. 不能在未通知贡献者的情况下追溯改变已发布版本的许可。
3. 不同仓库权益冲突时，以“更底层、更宽松”的许可为准；上层不能覆盖下层。
4. 商业条款与开源许可冲突时，先停止发布，咨询律师，不以“行业惯例”代替法律判断。
5. 所有决定记录在仓库的 `RIGHTS.md` 或 ADR 中，不能只留在聊天记录。

## 8. 数据与隐私

代码许可不授予用户数据权利。会话 JSONL、模型请求、工具输出、缓存可能包含敏感信息：

- 默认按敏感数据处理；日志脱敏、轮转、保留期限由宿主负责。
- 不使用用户数据训练模型，除非用户明确同意并有单独条款。
- 云端服务的隐私政策与服务条款独立于代码许可。
- 删除用户数据的能力必须真实可验证，不能只在文档承诺。
